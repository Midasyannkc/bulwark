# Bulwark

Security engineering tooling for a virtual-care company, built against the Rezilient Health Senior Security Engineer posting. It fills the four areas of that posting that a cloud-and-IAM project does not cover: **threat modeling and design review, incident response, audit evidence, and security of FHIR and partner integrations**.

It is a portfolio project, not a product. It uses real public reference data where reachable, says where data is invented, and records every bug it hit as an incident with a failing test and a separate fix commit.

## Results

All figures come from `python -m bulwark` (see `docs/REPORT.md`).

| Area | Result |
| --- | --- |
| Threat modeling | A 11-element, 10-flow data-flow model produces STRIDE threats, each mapped to a real ATT&CK technique and real NIST 800-53 controls; 0 citations fail to resolve against the real catalogs. Mutation tests remove TLS from every flow and encryption from every store and require a finding each time |
| Incident response | 3 runbooks (storage exposure, account compromise, ransomware) lint clean across 7 phases; a tabletop simulator scores a strong play at 100 and a weak play at 6; HIPAA breach deadlines are computed from the discovery date |
| Audit evidence | 15 controls mapped to SOC 2, HIPAA and HITRUST categories, collected into a hashed evidence package; the seeded snapshot yields 11 exceptions and 4 passes; coverage of the real NIST Moderate baseline is 19 of 177 base controls (10.7 percent), stated plainly |
| FHIR security | 7 synthetic resources validate against the real R4 definitions; de-identification leaves 0 identifiers; an in-process API blocks cross-patient reads, unscoped writes, unauthenticated bulk export and PHI in logs |
| Integrations | 3 partner profiles assessed: a well-run lab vendor has 0 findings, an EHR partner 8, a marketing vendor without a BAA 6 |
| Incidents | 10, each a failing-test commit and a separate fix commit, re-run by `make verify` |

## How the posting maps to the code

| Posting responsibility | Where |
| --- | --- |
| Lead threat modeling and security design reviews | `bulwark/threatmodel`, `data/model/cloudclinic.yml` |
| Incident response runbooks, tabletop exercises, technical lead in incidents | `bulwark/ir`, `data/ir/` |
| Evidence for SOC 2, HIPAA/HITECH, HITRUST; control testing | `bulwark/evidence`, `data/controls.yml` |
| Assess third-party integrations, APIs, EHR and partner data exchanges | `bulwark/fhir/integration.py`, `api.py`, `spec.py` |
| Protect PHI and PII; data classification and minimization | `bulwark/fhir/deid.py`, threat model data classes |
| Automate security processes through scripting | everything is Python with tests; `make report` |

Not rebuilt here, because the companion project **Warden** already covers it: AWS IAM and Terraform guardrails, vulnerability prioritization with CISA KEV, scanner pipelines, detection rules and the HIPAA technical safeguard map.

## Run it

```
make install
make test      # pytest
make report    # writes out/report.json and docs/REPORT.md
make verify    # re-runs every incident's reproduce and fix commits
```

## Real and invented

Real: NIST SP 800-53 rev5 catalog and Moderate baseline, MITRE ATT&CK enterprise techniques, HL7 FHIR R4 element definitions. See `data/SOURCE.md`.

Invented: the CloudClinic architecture, runbooks and scenarios, cloud snapshots, all FHIR patients and values, the API under test, and the partner profiles. Nothing describes Rezilient's real systems.

## Limits

- No live AWS account, SIEM, EHR, identity provider or auditor. Collectors read JSON shaped like AWS output, not the API.
- HIPAA, SOC 2 and HITRUST references are by ID or category name as I know them; the HITRUST CSF text is licensed and not used. Breach deadlines are an engineering aid, not legal advice.
- The tabletop uses scripted plays, so it tests the scoring, not a real team.
- The in-process API is small by design; it shows access-control and logging flaws, not every SMART on FHIR behavior.
- De-identification follows the Safe Harbor list for the fields this model carries. Names of other people in free text, and any other unique code, would still need review.
- The sampling policy is internal, not an audit standard.
